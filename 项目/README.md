# 线性代数基础 · 可视化项目

与《线性代数基础》正文配套的可交互项目。五个视角，一层设计。

## 这是什么

正文走到哪一步，这里就有哪一站。五个视角各自独立、都能单独打开，共用同一套配色、字体与页面外壳——点进任何一个模块，都知道自己还在同一个项目里。全部离线自足，**双击即可打开**（`file://` 下功能完整，零依赖、零联网）。

不想交互、只想读文章？`文章.html` 是正文的网页版：十四张图、十八个公式都在，公式由 KaTeX 服务端预渲染（`assets/katex/`），同样离线可读。

| 视角 | 模块 | 看什么 | 对应正文 |
|---|---|---|---|
| READ | `文章.html` | 正文网页版：全文 + 配图 + 公式 | 全篇 |
| VIEW 01 | `views/01-向量工场.html` | 一捆数：加减、数乘；首尾相接与平行四边形两条路同一个终点 | 第一站 |
| VIEW 02 | `views/02-矩阵作用台.html` | 一张表：作用在箭头上；两列的去向；面积放大倍数 | 第二站 |
| VIEW 03 | `views/03-先后有别.html` | 两张表连着摁：A·B ≠ B·A；可交换的反例 | 第三站 |
| VIEW 04 | `views/04-特征方向.html` | 变了又没变的方向；弹簧系统相图；越过临界阻尼那一刻 | 第四站 |
| VIEW 05 | `views/05-行列式与反作用.html` | 面积放大倍数；塌缩到 0；反推原因 | 第五、六站 |

导航首页：`index.html`

## 跑测试

```powershell
node tests/verify-core.cjs             # 38 项正向断言 + 6 组"把故障装回去"的反向对照
node tests/smoke-dom.cjs               # 五个视角的运行时冒烟
node tools/verify-repo-style.cjs       # 导航双向一致、共享层引用、无硬写界面色、文章页同源
node tools/verify-views-layout.cjs     # 真实浏览器：画布布局 + 取景（需 playwright-core + 本机 Chrome）
node tools/verify-views-layout.cjs --reverse   # 反向对照：把三个故障装回去，同一套断言必须报错
node tools/verify-views-layout.cjs --shots=tools/_shots   # 顺手截下每个场景（含修复前对照）
```

最后一条要单独说：它驱动本机 Chrome 打开 `file://` 下的五个视角，量
`getBoundingClientRect`，并把每个视角实际画出来的箭头端点、圆点、标签框记下来，
逐一对账"有没有跑到画外"；还会沿已知的世界坐标线段采样数颜色，对账"重合的两支箭头
是不是都还看得见"（单位表下 M·u 与 u 严格重合，画序一错就会退化成"一支箭头挂两个标签"）。
读源码看不到排版、DOM 桩件里没有排版——这条是补盲区的。
缺 playwright-core 或本机没有 Chrome/Edge 时它会明说「跳过／未执行，不是通过」并返回 2，
所以 CI 上少依赖不会被误当成绿。

仓库根还有一条文章页的保真校验（重新生成后必跑）：

```powershell
python tools/verify_article_html.py   # md 与 文章.html 的段落/图/公式全保真比对
```

正文网页版的再生成（md 改动后）：在仓库根 `E:\线性代数` 运行

```powershell
python tools/build_article_html.py
python tools/verify_article_html.py   # 重新生成后必须全保真
```

它解析 `线性代数基础·一捆数与一张表.md`，抽出公式交给 `项目/tools/katex_render.cjs` 预渲染，再拼出 `项目/文章.html`——产物无客户端 JS，公式是 KaTeX 服务端渲染的静态 markup。配图带 `loading="lazy"` 和真实宽高属性：长文不预载全部图片，滚动到才加载，且加载前就按真实比例占位，版面不跳。

## 统一性怎么保证

配色与排版只有 `assets/theme.css` 一处定义；页面外壳（顶栏 + 页脚）七个页面一致。这些不靠约定，靠 `tools/verify-repo-style.cjs` 判定：导航页与磁盘上的视角双向一致、每个视角都能回到导航页、都引用共享设计层与核心数学、`lang`/页脚齐备、样式块里没有硬写界面色、五个视角都不自带第二套 token；文章页另查：双向链接、KaTeX 资产齐全、14 张图落盘、公式是服务端预渲染产物、样式块同样不硬写界面色。

## 取景：画框怎么定

画框（`range`，即画框半高）在这套项目里不是装饰参数，而是一条**因变量**。

**规则：凡是被读者输入决定尺寸的东西，画框必须从它算出来，不能写死。** 五个视角里
`u`、`v`、`b`、`A`、`B`、`M` 全是可以填任意数的输入框——写死画框，读者一填大数，
结论就跑到画外，读数里量得出、图上却看不见。`assets/draw.js` 提供 `D.fitRange(点集)`
与 `D.gridStep(画框)`：视角只声明"这一帧哪些东西必须看得见"，取景与网格粗细由共享层算。
两条附加条件缺一不可：**取景阶梯取整**（否则拖一下抖一下）、**拖动期间冻结**（否则鼠标
底下的点会自己跑）。

**边界：取景与对象只能动一个。** 视角 04 的画面里有一张必须原地对读的单位网格——标尺一动，
"网格被摁弯了多少"就失去参照。所以 04 反过来做：画框固定，由 `clampProbe` 限制拖动行程，
使自检点被摁之后的像始终留在画框内，读数里照实说明"已经拖到行程尽头"。视角 03 是另一头：
两张图要比的是终点位置，各自取景会让比例不同、没法直接对照，于是取两者中装得下的那一个、
两张共用。

**"一整条"的长度也从取景算。** 特征方向线、塌缩方向线、延伸线要贯穿画框，用
`view.reach()` 取画框最远处；写死长度的话，画框一放大，它就从"一整条"缩成中间一小截。
标签位置同理，且要按横竖各自的比例折算——画框横向比纵向宽，沿单位方向走固定距离会
从短的那一边出去。

**不只是画框——凡与"看得见的东西"打交道的常量，都得跟着画框走。** 视角 02 的 `u` 也变成
可填的输入框之后，"拖绿箭头的头"这条交互里两处写死的常量立刻露馅：抓取半径写的是
**0.5 个世界单位**，而 `u` 一填到 (60, 40)，画框随之放大，这 0.5 在屏幕上只剩几个像素，
鼠标再也抓不住那个头；吸附步长写的是固定 0.1，画框小的时候（`u` 与 `M·u` 都贴近原点）
一格要跳屏幕上几十像素。改法：**抓取半径按屏幕像素判**（手感与画框无关），
**吸附步长按画框折算**（`画框 / 40`）。同一件事，视角 04 的 `clampProbe` 早就在做，只是
那里的常量是行程而不是半径。

**读数的一条边界：零捆不等于"恰好不动"。** `u` 填成 (0, 0) 时 `M·u` 当然等于 `u`，但那是
"没有东西可送"，不是"表恰好不动它"。零向量必须从"恰好不动"的判定里排除，否则读者会读到
"u 正落在长度不变的方向上"这句错话——而它听上去还挺有道理。

这些都由 `tools/verify-views-layout.cjs` 判定：每个视角、每个极端输入场景下，
画出来的箭头端点、圆点、标签框都必须落在画布内。

## 核心数学

`assets/core.js` 是纯计算层，不碰 DOM，因此可以被 `tests/verify-core.cjs` 直接 `require` 出来跑断言。记号与正文、与五个视角一致：

- `u`、`v`：一捆数（平面上从原点出发的箭头）
- `M`、`A`、`B`：一张表 `[[a,b],[c,d]]`，`M·u` 作用在 u 上
- `A·B`：先摁 B，再摁 A
- `λ`：特征方向上的放大倍数
- `det(M)`：作用对面积的放大倍数
- 弹簧系统 `m`、`k`、`c`：与第 10 篇一致

浏览器要求：任何现代浏览器（Canvas 2D）。无需服务器、无需联网。
