# 系统科学实践记录 · 张成 Span Lab

> 项目：`span-lab/`（独立于工作区其他项目）
> 实践日期：2026-10-19
> 方法：系统内外因辩证生产法（七步）

## 0. 一句话结论

这次生产的核心不是"把三个向量画出来"，而是**把"张成"从一条定义变成一个可操作、可验证、可扩展的交互对象**：输入具体坐标与数量 → 判定秩与方程 → 在二维/三维中呈现对应的子空间 → 用整数组合点阵给出"所有线性组合"的可见见证。生产过程中真正的偏差不在数学，而在**工具系统的内因**（浏览器无头模式的最小视口、PowerShell 的默认编码、3D 全空间的可视化表达），这些偏差都被记录并修正。

## 1. 第一步：解析人系统的要求

### 1.1 显式要求

1. 做一个**交互可视化项目**，同时包含二维与三维空间。
2. 能**具体填写基向量的数值**，也能**决定基向量的数量**。
3. 点击后**展现这组基能够描述的空间**；二维、三维中对应的空间要有对应反应。
4. **先做核心功能**，以后可能扩展，要求架构上做好准备。
5. **不要采用本工作区已有文件的内容**；本项目要与其他项目区分。
6. 进行**系统科学实践**。

### 1.2 隐含约束（从表述与工作区推断，非用户明说）

- 使用场景偏**教学 / 自助探索**：工作区里已有线性代数文章与配图，这个工具很可能承担"让读者自己动手"的那条腿。因此：
  - 结论必须**数学正确**，不能只是好看；
  - 术语要能落到具体数字与方程上；
  - 首次使用不能有构建步骤或网络依赖。
- "基的数量"可能大于空间维数（例如三维里放四个向量），所以必须能表达**冗余 / 秩不足**，而不只是"满秩才好看"。
- 二维/三维都必须是**真实可操作**的，不能只是一张示意图。
- "以后扩展"意味着不能把 2 和 3 写死在一个巨型函数里；数学、渲染、界面要分层。

### 1.3 要求背后的外部系统

- **线性代数教学系统**：span、秩、线性无关、子空间方程是课程的核心概念；教学上的难点不是定义，而是"为什么多个向量不多出维数""为什么三维里的两个方向只能铺一张平面"。
- **文章/出版系统**：工作区中的文章项目需要"图像说形 + 可交互说'你自己试'"的配套物；交互页必须能离线打开、截图可读、不依赖 CDN。
- **读者所在环境**：Windows + 现代浏览器，可能没有 Node；因此 `file://` 双击可开是硬约束。
- **视觉参照系统**：人系统指定 `D:\汽车悬挂系统\悬挂系统内因篇（下）·现实悬挂系统的内因.html` 作为艺术风格参照。只借鉴它的视觉语言（深灰底、单一青色强调、细边框、大行距、眉标/公式卡/文章式排版），不复制其文字、插图或代码。

### 1.4 验收标准（本次采用）

| 维度 | 判据 |
|---|---|
| 数学 | 0/1/2/3 维四类结果、共线/共面/零向量/空集/分数/冗余向量全部正确 |
| 交互 | 能改数量与数值；点击后结果与画布同步；二维/三维各自独立 |
| 视觉 | 直线、平面、全空间三种形态可区分；点阵确实落在子空间里 |
| 工程 | 离线可开；无外部依赖；无启动错误；有可重复的验收命令 |
| 扩展 | 数学内核与渲染/界面解耦，新增预设或视觉层不需要重写核心 |

## 2. 第二步：认知自身内因

### 2.1 已知

- 线性代数：秩、RREF、张成、法向量、参数方程、行列式与面积/体积。
- 前端：Canvas 2D、透视投影、DOM 事件、CSS 布局、`file://` 与 HTTP 的差异。
- 工程：Node 测试、无头浏览器截图、`--dump-dom`。

### 2.2 能力边界与易错点

- **不能直接"看见"页面**：必须依赖截图或 DOM 读数；截图会骗人（见第 6 节）。
- **视觉自评容易替代数学验收**：图好看不等于秩对。对策是把数学内核抽成纯函数，先用 17 条断言钉死。

- **上下文有限**：不适合一次写一个巨型文件；按数学 / 工具 / 渲染 / 界面拆分，每层可独立测试。
- **对工具默认行为不能想当然**：PowerShell 的默认编码、无头浏览器的最小窗口、`file://` 的模块限制，都是本轮实际撞到的。

### 2.3 需要外部系统支持的部分

- 真实浏览器的渲染与截图（Node 只能验证数学与绘制调用，不能验证"看起来对不对"）。
- 人系统对"这个可视化是否真的有助于理解"的最终判断——本轮只能给出可检验的中间判据。

## 3. 第三步：分析工具系统（内因、作用预测、反作用）

| 工具 | 它的内因 | 我的作用预测 | 实际反作用 / 结果 |
|---|---|---|---|
| 浏览器 Canvas 2D | 即时模式；`canvas.width` 会重置上下文；DPR 需手动处理；`opacity` 类呈现无法用 DOM 断言验证 | 可用纯 Canvas 画网格、箭头、半透明面、点阵 | 成立；用 `setTransform(dpr,…)` 与 ResizeObserver 解决高分屏与尺寸 |
| `file://` | ES module 与 `fetch` 受同源限制；classic script 不受影响 | 用 classic script + UMD，双击可开 | 成立；没有构建步骤，`file://` 下 14/14 自测通过 |
| Node | 可 `require` UMD；无 DOM/Canvas；`requestAnimationFrame` 不存在 | 数学与渲染器都能在 Node 里跑；rAF 需降级为同步 render | 成立；假 canvas + 记录型上下文跑通 13 条渲染断言 |
| 无头 Edge / Chrome | 可 `--screenshot`、`--dump-dom`；**布局视口有最小宽度**；rAF 受虚拟时间影响 | 可以截图做视觉终审、用 dump-dom 读自测报告 | 截图可用；但 `--window-size=390` 的实际 `clientWidth` 是 **481**（Edge）/ **489**（Chrome），截图是裁切而非真实 390 视口 |
| PowerShell（本机） | 文本读写受默认编码影响；`Get-Content -Raw` + `Set-Content` 处理含中文的 UTF-8 源文件会按 ANSI 解码 | 只用来列目录、起服务、跑测试 | **实际踩坑**：一次批量替换把两个渲染器的中文注释与字符串写成乱码，导致 `SyntaxError`；改用写文件工具 / Node 重写，不再用 PowerShell 改源码 |
| CDN / Three.js | 取回时间不可控；离线不可用；版本与安全策略是外部条件 | 不引入；自研投影 | 成立；页面完全离线，无网络请求 |

### 3.1 关键取舍：为什么不用 Three.js

- Three.js 的 3D 质量更高，但会引入：CDN 取回时间、离线不可用、透明面排序、额外构建/版本问题。
- 本项目的几何非常克制（轴、网格、箭头、半透明平面、点阵），用自研透视投影足够，而且：
  - 与 2D 共享同一套视觉语言；
  - `project()` 是纯函数，可在 Node 里用解析不变量测试；
  - 不透明面/半透明面的顺序可以自己控制。
- 代价：没有光照与阴影，视觉上限低于 Three.js；本轮接受这个代价，把精力放在数学表达与验收上。

### 3.2 关键取舍：双工作区 vs 单工作区切换

- 需求是"里面有二维和三维空间"，且两者都要有反应。
- 选择**并排双工作区**：各自有独立的向量、数量、视角和结果；宽屏并排，窄屏上下堆叠。
- 这比"一个工作区 + 维度切换"更符合"同时看到两个世界"的直觉，也让"二维整个平面"与"三维里的一张平面"形成对照。
- 代价：页面更长、两套编辑器；用 `WorldPanel` 复用解决。

## 5. 第五步：实践与偏差记录

### 5.1 实际发生的偏差（按时间）

1. **首屏空白 / 只有一张空卡**
   - 现象：页面渲染出 2D 卡片骨架，但无向量行、画布空白，3D 卡片为空。
   - 定位：页面内可见错误面捕获到 `Uncaught ReferenceError: global is not defined`，位置在 `scene2d.js` 的 ResizeObserver 回调。
   - 原因：UMD 工厂内部误用了外层参数名 `global`；工厂作用域里只有 `globalThis`。
   - 修正：`global.devicePixelRatio` → `globalThis.devicePixelRatio`。
   - 教训：**页面要自带可见错误面**，否则"空白"只能靠猜；`--dump-dom` 能直接读出错误。

2. **PowerShell 批量替换把中文源码写坏**
   - 现象：`SyntaxError: Unexpected identifier '杩樻病鏈夊悜閲'`。
   - 原因：本机 PowerShell 在无 BOM 的 UTF-8 源码上按 ANSI 解释，`Get-Content -Raw` + `Set-Content` 造成有损转码。
   - 修正：不再用 PowerShell 改写源码；用写文件工具或 Node（UTF-8）重写。重写后 `node --check` 全绿。
   - 教训：工具系统的编码内因不会因为"我只是替换一个词"而消失；源码改写要走 UTF-8 明确的通道。

3. **3D 全空间的表达经历了三次迭代**
   - 第 1 版：画"基本平行六面体"（三个基向量的 0/1 组合）。实际渲染时远角 `u+v+w` 常被裁出视口，看起来像一块悬空的碎片。
   - 第 2 版：只画点阵。空间感不足，画面像稀疏的星点。
   - 第 3 版：**三维整数格线 + 点阵 + 中心径向微光**。格线沿三个基方向连接相邻整数点，填满视域；点阵保留"组合"的语义。
   - 教训：表达"无限空间"时，**离散格线比一个有限盒子更不容易误导**；有限的平行六面体容易被读成"张成就是这个盒子"。

4. **并排卡片等高造成 2D 卡片大片空白**
   - 现象：为对齐底边使用 grid stretch + `margin-top:auto`，当三维分析区展开时，二维卡片被拉到同高，按钮与分析区之间出现明显空白。
   - 修正：撤掉等高约束，恢复 `align-items: start`；接受两张卡片底边不齐，换取内容紧凑。
   - 教训：布局的"整齐"不能以制造空洞为代价；先问这个整齐服务于什么。

5. **390px "手机截图"看起来横向溢出**
   - 现象：Edge `--window-size=390,844` 截图里卡片右侧被裁、方法说明按钮不见。
   - 定位：`?debug=1` 把 `clientWidth / scrollWidth / card / coords / input` 写进 DOM → `clientWidth=481`、`scrollWidth=481`、`card=457`；Chrome 同样为 489。
   - 结论：**不是布局溢出，是无头浏览器的最小布局宽度 + 截图裁切**。真正 500px 截图布局正常。
   - 教训：判断响应式是否溢出，读 `scrollWidth` 与 `clientWidth`，或用 CDP 设备仿真；不要用一张小于最小视口的截图下结论。

6. **坐标轴 `x` 标签被裁到画布边缘**
   - 现象：2D 画布右端的 `x` 只显示一半。
   - 修正：标签改为 `align:'right'`，位置 `w-12`。
   - 教训：Canvas 文字没有 CSS 的 `overflow`，所有边缘标签都要按对齐方式预留宽度。

7. **视觉重做：从"仪表盘"改为参照文章风格**
   - 现象：初版是 1680px 宽的深色仪表盘：径向渐变背景、发光线条、14px 正文、密集小标签。参照页是 860px 单栏文章：`#161618` 底、`#00adb5` 单一强调、1px 边框、16.5px/1.95 行距、眉标 + 公式卡 + station 卡。
   - 修正：改为 1120px 双栏 station（窄屏回到 860px 单栏），加入眉标、lede 左边线、居中公式卡、青色细边卡与 station 头；去掉背景网格与页面光晕，统一 span/轴/向量的颜色；正文与标签字号整体上调。
   - 新差异：`?demo=analysis` 打开分析区后，两张画布变成全黑。定位：`<details>` 展开改变了布局，ResizeObserver 触发 `resize()`，设置 `canvas.width/height` 会清空画布，而重绘只挂在 `requestAnimationFrame` 上；无头截图在 rAF 之前落帧。修正：`resize()` 末尾改为**同步 `render()`**。这与既有"不要把推进/验收挂在调度器上"同构。
   - 教训：**尺寸变化本身会清空画布，"等下一帧再画"等于给空白留了一个窗口**；凡是会清空承载物的操作，都要在同一条同步路径里补画。

### 5.2 没有被偏差推翻的预测

- 无头浏览器 `--dump-dom` 可以读页面内自测报告 → 成立（14 条）。
- 纯 Canvas 3D 足够表达轴、网格、箭头、半透明面和点阵 → 成立。

## 6. 第六步：复盘

### 6.1 预测 vs 实际

| 预测 | 实际 | 偏差性质 |
|---|---|---|
| 首屏应直接可用 | 首屏因 `global` 报错空白 | 实现错误；可见错误面把它暴露 |
| 3D 用平行六面体表达满秩 | 被裁切、语义误导 | 表达设计错误；迭代为格线点阵 |
| 无头浏览器 390 宽 = 手机视口 | 实际 481/489；截图是裁切 | 工具内因误判；改读 DOM 宽度 |
| PowerShell 可以安全改源码 | 中文被写成乱码 | 工具编码内因；改用 UTF-8 通道 |
| 双卡等高更整齐 | 产生大片空白 | 审美假设错误；回退 |
| 视觉风格只需换配色 | 还需改字号、行距、边框、宽度与卡片结构；展开分析时画布曾被清空 | 风格是系统，不是调色板 |

### 6.2 可复用的做法

1. **先钉数学，再谈视觉**：纯函数 + Node 断言；渲染器只负责"把已判定的信息画出来"。
2. **渲染器接受注入的 canvas，并暴露纯投影函数与 `stats`**：这样同一份渲染代码既能在浏览器跑，也能在 Node 里用记录型上下文验收。
3. **页面自带错误面 + URL 自测入口**：`#boot-error`、`?selftest=1`、`?debug=1`；出错时不用猜控制台。
4. **表达"无限"时优先离散见证物**：整数格线/点阵比有限半透明盒子更不容易被误读，也更容易写断言（点必须满足子空间方程）。
5. **截图只作终审**：结构、数值、投影不变量先在 Node 里验；截图用于看层级、对比度、遮挡、边缘裁切。
6. **窄屏验收先量 `scrollWidth`**，再决定是否改 CSS。

### 6.3 还没做、但已留好接口的

- 把当前状态序列化到 URL hash / localStorage（`WorldPanel.state` 已集中）。
- 四维或一般 `n` 维的投影视图（数学内核按 `dim` 工作；渲染器与轴配置需要新增）。
- 基变换动画（从一组基连续变到另一组）。
- 零空间、投影、特征向量的叠加层。
- 让点阵的"组合系数"可点击/可高亮（探针已经给出单个组合点）。

## 7. 第七步：理论反作用

本轮向 `dialectical-systems-production` 的第四层子系统 `tools/web-frontend.md` 追加了**两条待验证假设**（只增不改），并通过 `board.mjs add` 同步英文镜像、重建面板；两次 `check` 均为 `IN SYNC`：

> **无头 Chromium 的最小布局视口约 481–489 CSS px**：`--window-size=390,844` 生成的 PNG 是 390 px，但页面里的 `document.documentElement.clientWidth` 是 481（Edge）/ 489（Chrome），`scrollWidth == clientWidth`，卡片实际宽 457。因此"截图里右侧被裁"不等于"布局横向溢出"；判断响应式是否溢出必须读 DOM 宽高（或使用 CDP 设备仿真），不能只看截图。

> **给 canvas 赋 width/height 会重置位图**：`ResizeObserver` 里改尺寸后只把重绘排进 rAF，截图（或后台标签页）会在补画之前落帧，看到整块黑画布。凡"清空承载物"的操作，都要在同一条同步调用链里立即补画。

第一条是既有"截图目测会漏掉结构缺陷"的具体补充：**截图连"视口是多少"都可能不是你以为的那个数**。第二条是既有"不要把推进/验收挂在调度器上"在**画布被清空**这一具体事件上的同构。

未对 `SKILL.md` 第一层一般规律作任何评论；如认为一般规律需要修改，按第七步第 4 点应在项目完成后转告人系统，经同意后再写入。
